## 2. What real data is missing?

1. **Historical rooftop PV production** (MW, per district or national), at any resolution — **not present** in any supplied file. Confirmed by inspecting all 5 project files (2 Prosol PDF dashboards, 1 load-shedding CDC, 1 PV-forecast concept note, this CDC) plus the two uploads: none contain a production time series (timestamp -> MW).
2. **Historical weather** — no file supplied. The architecture targets the Open-Meteo Historical Weather API (`archive-api.open-meteo.com/v1/archive`) as the real source (`src/ingestion/weather_provider.py::OpenMeteoProvider`).
3. **Forecast (NWP) weather** — same provider family, `api.open-meteo.com/v1/forecast`.

## 3. Environment limitation encountered while building this repo

This build/demo sandbox restricts outbound network access to a short allow-list (pypi, npm, github, etc.) that **does not include `open-meteo.com`**. A live test returned `403 Forbidden` at the egress proxy. Consequently:

- `OpenMeteoProvider` is fully implemented and ready to run, but **could not be executed here** to fetch real weather.
- `data/processed/weather_historical.csv` shipped in this repo was generated by the **documented fallback**, `SyntheticClearSkyProvider` (pvlib Ineichen clear-sky model + a seeded stochastic cloud-attenuation process). Every row is tagged `weather_source = SYNTHETIC_CLEARSKY`.
- **Action for the team:** run `python scripts/02_build_weather_dataset.py` from any machine/CI runner with normal internet access. No code changes are needed — the pipeline is provider-agnostic; only `weather.provider` in `configs/config.yaml` matters, and it is already set to `open_meteo`.

## 4. What can be trained *now*?

- **Physics baseline** (`src/physics/pv_model.py`): fully real physics (pvlib solar position + Ineichen clear-sky + NOCT cell-temperature + linear temperature derating), driven by real fleet capacity and (currently synthetic, swappable to real) weather. This is usable today as fallback Level 3 (CDC section 18) regardless of weather source.
- **Full ML pipeline (RF/LightGBM/TFT, uncertainty, correction, hierarchical reconciliation)** — architecturally ready, but **empirically meaningless until run against real weather and, ideally, real production**. Training against synthetic weather + physics-derived proxy production would only teach the model to re-derive the physics equation — reported metrics from that would not reflect real-world skill and must not be presented as validation results (CDC Rule 2).

## 5. What can only be demonstrated (not empirically validated)?

Everything downstream of production data: model comparison tables, backtested MAE/RMSE, uncertainty coverage, drift detection thresholds. These are demonstrated on the **labelled DEMO/PROXY** dataset (`data/processed/training_dataset_15min.csv`, column `pv_production_mw_proxy`, `pv_production_source = DEMO_PROXY_PHYSICS_SIMULATION`) to prove the pipeline is complete and correct — never presented as real STEG measurements or real model skill.

## 8. Data category classification (CDC continuation §31)

**REAL**
- `data/raw/pv_fleet_prosol_3_snapshots.csv` (official Prosol snapshots)

**DERIVED** (computed from REAL data via documented, deterministic transforms)
- `capacity_mw` per (district, timestamp) — linear interpolation of the REAL snapshots
- Solar geometry (elevation, azimuth, clear-sky GHI/DNI/DHI) — pvlib, function of (lat, lon, timestamp) only
- Hierarchical (governorate/national) forecasts — exact sums of district-level values

**MODEL OUTPUT**
- Persistence / seasonal persistence / physics / LightGBM point forecasts
- P10-P90 quantile forecasts (quantile LightGBM + split-conformal)
- Corrected forecasts (raw + residual correction)
- All reported in `reports/MODEL_VALIDATION_REPORT.md`, always against the DEMO/PROXY target — never described as validated real-world performance

**DEMO ONLY**
- `weather_historical*.csv` (tagged `weather_source=SYNTHETIC_CLEARSKY`) — real provider (`OpenMeteoProvider`) implemented but unreachable from this build sandbox (HTTP 403); confirmed reachable via a third-party wrapper at **daily** resolution only (see `docs/REAL_PRODUCTION_DATA_SOURCES.md §4`)
- `pv_production_mw_proxy` (tagged `pv_production_source=DEMO_PROXY_PHYSICS_SIMULATION`) — no real measured PV production source exists publicly for Tunisia (see `docs/REAL_PRODUCTION_DATA_SOURCES.md`)

**Enforcement, not just labelling:** `DATA_MODE=real` (see `src/ingestion/data_mode.py`) makes the weather-ingestion and dataset-build scripts **raise and exit non-zero** rather than silently substituting DEMO ONLY data — verified by direct test run (see `docs/REQUIREMENTS_TRACEABILITY_MATRIX.md`).
